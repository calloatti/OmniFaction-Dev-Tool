Apply in `Version-1.0/Source/WorkSystemPatches.cs`:
1. Remove `using Timberborn.Bots;` (no longer referenced once the exemption is gone).
2. Replace the beaver-exempt compatibility checks with a direct `CanWorkAt` check — 3 sites, all currently `bool isBot = worker.GetComponent<Bot>() != null;` + `if (!isBot || FactionAssignmentHelper.CanWorkAt(...))`:
   - unemployed-fill loop (site 1),
   - backward migration search (site 2),
   - migration loop (site 3, has a blank line between the two lines).
3. Copy the doc comment from `Version-1.1` `Patch_WorkplaceAssigner_Assign` explaining the beaver restriction.

## Change 4 — Modded-faction beaver support (Emberpelts, first one-by-one)

`Version-1.0/` content only (no source change). Full pattern + verification in `../modded-faction-beavers.md`. Summary:
- Added `Characters/Beaver/Beaver{Adult,Child}.Emberpelts.blueprint.json` — copies of the vanilla shared beaver blueprints with `TemplateName` suffixed `.Emberpelts`.
- Added `TemplateCollections/TemplateCollection.Characters.Emberpelts.blueprint.json` — **standalone** spec (`CollectionId: "Characters.Emberpelts"`, full `Blueprints` array). `TemplateCollectionService.Load` unions blueprints across all specs sharing a `CollectionId`, so it merges with the Emberpelts mod's own collection regardless of load order; harmless orphan when the mod is absent.
- `manifest.json` gained `"OptionalMods": [{"Id": "Emberpelts"}]` (soft-ordering/documentation only — NOT hard-enforced, see below).

Empirically: only Folktails/IronTeeth spawned until OmniFaction loaded after Emberpelts.
- Next modded faction: repeat the same recipe (see `modded-faction-beavers.md`), no code changes needed — the round-robin `PickTemplate` pool picks up any `IsFactioned` template automatically.

## Change 5 — DC-faction starting population + service rename to `OmniFactionService`

Renamed the counter singleton `FactionPopulationService` → `OmniFactionService` (file, class, and `OmniFactionConfigurator`) when it gained the per-faction starting-population spawn. **1.0-only so far** — `Version-1.1/` still uses the old name until ported.
- `OmniFactionService` now injects `BeaverFactory`, `ISceneLoader`, `GameModeSpecService` and, on `EnteredFinishedStateEvent` for a `DistrictCenter` in a live game, replicates the new-game start for that DC's faction exactly as `StartingBeaversInitializer` + `StartingGoodsProvider` do (`Timberborn.GameStartup.cs`): spawns `GameModeSpec.StartingAdults`/`StartingChildren` at the DC's `BuildingAccessible.Accessible.UnblockedSingleAccess` with the mode's `AdultAgeProgress`/`ChildAgeProgress` spread, then gives `StartingFood` (Berries) + `StartingWater` (Water) into the DC's `SimpleOutputInventory.Inventory` via `GiveIgnoringCapacity`.
- Faction threaded through `CreateAdult`/`CreateChild` via new static `StartingBeaverSpawn.PendingFaction` in `BeaversPatches.cs` (set around the spawn calls only); `CreateChild` falls back through it after `Patch_NewbornSpawner.PendingFaction`.
- **Reload-safety:** gated on `StartupComplete` (static, set by `OnShowPrimaryUI`). Restored buildings re-post `EnteredFinishedStateEvent` when `EventBus.PostLoad()` drains queued events — before `GameInitializer` posts `ShowPrimaryUIEvent` — so the starting settlement DC (new game) and every existing DC (save load) are skipped and never respawn. Live-play spawn also skipped for `"Common"` factions and any faction that already has beavers (starting faction untouched; a wiped-out faction restarts from a new DC).
- **Starting-settlement fix (runtime bug):** the game's own starting-spawn (`StartingBeaversInitializer` → `BeaverFactory.CreateAdult/CreateChild`) routes through the mod's `Create*` prefixes, which were round-robining — so the first DC got mixed-faction beavers. Fixed by a startup fallback in the prefixes: while `!OmniFactionService.StartupComplete` (the game's starting-spawn window, new game only — `GameStarter.Load` only spawns the starting building on new game), they use the starting faction via `PickAdultTemplateForStartupFaction`/`PickChildTemplateForStartupFaction` (`OmniFactionService.CurrentFaction` = `FactionService.Current.Id`), before round-robin. No patch on the game's DC spawn needed — `StartingBuildingSpawner.Load` (GameStartup.cs L766) already builds the starting DC from `_factionService.Current.StartingBuildingId`, so `FactionService.Current` is guaranteed set before any starting beaver spawns.
- **Language-independent faction identity (runtime bug):** Emberpelts buildings (DC included) resolved to their `DisplayNameLocKey` (`"Faction.Emberpelts.DisplayName"`) instead of the faction id, so faction lookups failed — modded-faction buildings fell through to `"Common"` and the DC starting-population spawn was skipped. `FactionBlueprintCache` now also maps `TemplateName → FactionSpec.Id` (`TemplateToFactionId`); `FactionAssignmentHelper.GetFactionID` reads that map (never locKeys) and falls back to substring-matching the entity/template name against every loaded faction id (`FactionNeedCache.FactionAllowedNeeds.Keys`). The `TemplateToFactionLocKey` map is display-only (the `LabeledEntity` suffix still resolves it through `ILoc`). Verified against `Faction.Emberpelts.blueprint.json` (`Id: "Emberpelts"`, `DisplayNameLocKey: "Faction.Emberpelts.DisplayName"`).
- Game mode read via `ISceneLoader.TryGetSceneParameters<GameSceneParameters>()` when `NewGame`, else `GameModeSpecService.GetDefaultSpec()` — mirrors the game's own fallback (`BadtideWeather.Load`, `HazardousWeatherSystem.cs` L334–341).
- Verified public APIs (no new Publicize needed): `GameModeSpec`/`MinMaxSpec<T>` (`Timberborn.NewGameConfigurationSystem`), `GameSceneParameters` (`Timberborn.GameSceneLoading`), `ISceneLoader` (`Timberborn.SceneLoading`), `ShowPrimaryUIEvent` (`Timberborn.UILayoutSystem`), `SimpleOutputInventory` (`Timberborn.SimpleOutputBuildings`), `GoodAmount` (`Timberborn.Goods`), `BuildingAccessible` (`Timberborn.Buildings`), `Accessible.UnblockedSingleAccess` (`Timberborn.Navigation`), `BeaverFactory.CreateAdult/CreateChild` (`Timberborn.Beavers`). `BlockObject.Load` sets state directly, but `PostInitializeEntity` → `Initialize()` → `NotifyOnStateEntered()` re-posts finished-state events for restored buildings — the `_startupComplete` guard handles that.

## Change 6 — Per-entity faction avatars + all-faction worker outfits (1.0-only, not ported to 1.1)

Audit of every `FactionService.Current` read site showed the mod only patched the content/crash-critical ones (the four collection-ID providers + `BeaverTextureSetter`). Unpatched beaver/bot reads now fixed:
- `BeaverEntityBadge.GetEntityAvatar` / `BotEntityBadge.GetEntityAvatar` (new `EntityAvatarPatches.cs`) — the selected character's portrait was rendered from `FactionService.Current`'s avatar, so every character showed the current faction's face. Postfixes reroute to the entity's own faction via `EntityFactionAvatarHelper.ResolveFaction` (substring-matches `GameObject.name` against `FactionSpecService.Factions`, same as `Patch_BeaverTextureSetter_Start`), preserving the contaminated/child/bot variants; unsuffixed entities keep the vanilla fallback. `FactionSpecService` reached via `__instance._factionService._factionSpecService` (both already publicized).
- `WorkerOutfitService.Load` (new `WorkerOutfitPatches.cs`) — the outfit dictionary was built from **only** `FactionService.Current.Id`'s `WorkerOutfitSpec`s, so a non-current-faction beaver/bot couldn't resolve its workplace's outfit. Postfix unions every other faction's specs into `_workerOutfitSpecs` (`GetSpecKey(s.Id, s.WorkerType)` never collides — outfit ids embed the faction). Required adding `Timberborn.WorkerOutfitSystem` to `CommonModSettings.props` Publicize (`WorkerOutfitService`, `WorkerOutfitSpec`, `GetSpecKey`, `_workerOutfitSpecs`, `_specService` all needed publicizing).
- Empty-slot placeholders (new `EmptySlotAvatarPatches.cs`) — a building's vacant character slots (dwelling lodges, workplace rows) rendered `FactionService.Current`'s avatar as the disabled placeholder. `Patch_WorkerView_ShowEmpty` (workplace faction from `_workplaceWorkerType`, a `BaseComponent` on the workplace), `Patch_DwellingUserFragment_ShowFragment`/`UpdateFragment` (dwelling faction from `_dwelling`; `ShowFragment` reads the `entity` arg because the prefix runs before `_dwelling` is assigned) push the building's faction into `EntityFactionAvatarHelper.PendingEmptySlotFaction` (prefix set / postfix clear, so the value never leaks across panels); `CharacterButton.ShowAdultEmpty`/`ShowChildEmpty`/`ShowBotEmpty` postfixes swap the background to that building's `Avatar`/`ChildAvatar`/`BotAvatar`. Required adding `Timberborn.CharactersUI`, `Timberborn.DwellingSystemUI`, `Timberborn.WorkSystemUI` to `CommonModSettings.props` Publicize.
- Intentionally **not** patched: `PathSystem` path/roof materials (global, no per-entity faction), `WellbeingUI` `FactionIcon`, and all single-faction meta reads (achievements, game over, wonder completion, tutorials, faction goals).
- 1.1 verified to have the same targets at near-identical lines (BeaversUI:790, BotsUI:224, WorkerOutfitSystem:463) — port is a straight copy of the two files + the `CommonModSettings.props` Publicize entry when desired.

## Change 7 — Bobingabout Script Pack compatibility (1.0-only, not ported to 1.1)

The "Bobingabout Script Pack" `CharacterCustomizer` (workshop 3416879061) overwrites the mod's faction furs/avatars with current-faction defaults when installed: its `CharacterTextureSetter` is added as a decorator on `BeaverTextureSetter` and its `Start` re-picks `FactionService.Current.Textures/ChildTextures` on every spawn/grow-up/save-restore (hardcoded fallback — verified from IL, empty-blueprint override wouldn't stop it), and its `CharacterAvatarSetter` is a competing `IEntityBadge` that wins over the vanilla badges.
- New `BobingaboutCompatPatches.cs` — `BobingaboutCompat.TryApply(harmony)` resolves the two types **by name** (`Type.GetType("Bobingabout.CharacterCustomizer.{CharacterTextureSetter,CharacterAvatarSetter}, Bobingabout.CharacterCustomizer")`) and, only when present, patches `AccessTools.Method(type, "SetTexture")` / `"GetEntityAvatar"` postfixes. Applied from `ModStarter` (`StartMod` after `PatchAll`, plus an `AppDomain.AssemblyLoad` retry for load-order safety). **Deliberate, documented exception to the no-reflection rule** — the rule protects game internals covered by publicizer; optional third-party interop has no compile-time mechanism.
- `SetTexturePostfix` re-applies the entity's own faction fur (shared `FactionFurHelper`, extracted from the `BeaverTextureSetter.Start` prefix into `BeaversPatches.cs`); `GetEntityAvatarPostfix` overrides the portrait with the entity's faction avatar preserving contaminated/child/bot variants. Both skip `"Emberpelts"` — the Script Pack ships that faction's art (`CharacterAvatarMap.Emberpelts.RedOnly`, grow-up maps), so Bobingabout handles it.
- Build green (0 warnings / 0 errors), deployed.

## Change 8 — Nearest-DC spawns, vanilla need order, crossing wildcard, assigner migration fix (1.0-only, not ported to 1.1)

- **Nearest-DC faction fallback for spawns:** new static `OmniFactionService.FindNearestDistrictFaction(position)` scans `DistrictCenterRegistry.FinishedDistrictCenters` for the DC nearest by distance and returns its faction (`null` when none, or when the nearest DC is `"Common"`). The `BeaverFactory.CreateAdult`/`CreateChild` and `BotFactory.Create` prefixes now insert it after the building/DC-spawn/startup faction sources and before round-robin, so a beaver or bot spawned near a faction's DC becomes that faction. `CreateNewbornAdult`/`CreateAdultFromChild` deliberately unchanged (building/child faction wins, round-robin fallback).
- **Vanilla need order restored:** `Patch_NeedVerifier_Load` buckets each `NeedSpec` by exact `CharacterType` (`"Beaver"`/`"Bot"`; specs with neither are in no list — matches vanilla `FactionNeedService.GetBeaverNeeds`/`GetBotNeeds`), then sorts each list by `NeedSpec.Order` with a loader-index tie-break (stable — mirrors vanilla's LINQ `OrderBy` over `GetSpecs<NeedSpec>()`). Fixes needs displaying alphabetically (loader order) instead of vanilla order in the UI.
- **District Crossing staffing exemption:** new `FactionAssignmentHelper.GetWorkplaceFaction(workplace)` returns `"Common"` for `DistrictCrossing` (a crossing links two districts and must be staffable by any faction regardless of its factioned template); `Patch_WorkplaceAssigner_Assign` uses it for the workplace side of `CanWorkAt`.
- **Workplace assigner migration fix:** the prefix no longer early-returns when there are no unemployed workers — the `HashSet` fill loop no-ops, then the migration pass from lower-priority workplaces still runs (matches vanilla `ReassignWorkersToHigherPriorityWorkplaces`). It also iterates **every** understaffed workplace per tick (no single-workplace early return). Paused workplaces are skipped automatically — `Understaffed` is false when the `BlockableObject` is blocked (decompiled `Timberborn.WorkSystem.cs` L1473–1483).
- **Bobingabout Script Pack compat reverted** (removes Change 7): `BobingaboutCompatPatches.cs` deleted, `ModStarter` back to plain `Harmony.PatchAll()` — the reflection-based interop had no compile-time safety. Root `AGENTS.md` row removed; `FactionFurHelper` still lives in `BeaversPatches.cs` (used by the `BeaverTextureSetter` prefix).
